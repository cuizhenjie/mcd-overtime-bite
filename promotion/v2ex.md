> 参赛作品 · 麦当劳程序员创意开发大赛
> https://github.com/cuizhenjie/mcd-overtime-bite

20:47，第八版方案改到第三轮，饿得手抖。打开外卖 App 翻了两屏又退出去——不是不想点，是不想再做这个决策。

于是写了个东西：**到点了，它自己点。**

## 它做什么

按「时间 + 位置 + 你的历史口味 + 30 元预算上限」，在加班晚餐时段自动完成：领券 → 选渠道 → 凑组合 → 算价 → 下单。

定位上刻意避开了"省钱精算"（同赛道已经好几个了），**入口是时间，省钱降级为预算硬约束**：

| | 省钱类项目 | 这个 |
|---|---|---|
| 起点 | 用户主动提问 | 时间自己走到点 |
| 交付 | 推荐几个方案让人选 | 直接下单 |
| 价格角色 | 优化目标 | 预算硬约束 |
| 关键洞察 | 用券省多少 | 配送费占预算多少 |
| 个性化 | 问用户想吃什么 | 从历史订单自己学 |

## 真实跑通的结果

用我自己的账户，接真实麦当劳 MCP：

```
门店：麦当劳(北京马家堡路餐厅)  1950609   467m
在售餐品：115 个
可用券：3 张（免费脆薯饼 / 人气麦旋风买一送一 / 9.9元中杯冰美式）

最优方案：
  麦辣鸡腿汉堡   原价 ¥22.50  →  券后 ¥11.90
  灰焰圆筒       ¥5.00
  到店取餐
  合计 ¥16.90      预算上限 ¥30  →  省 ¥13.10
```

核心逻辑零第三方依赖，67 个测试全绿（`9+14+15+9+20`），前 61 个不需要 Token。

## 8 个坑（这才是重点）

官方文档能查到工具名，查不到参数形状和返回结构。

**1. ClientSession 在第一次调用之前就死了。**
MCP 的 `ClientSession` 由 anyio task group 支撑，`async with` 一退出 `__aexit__` 就 cancel 掉整个 task group。我最初的连接协程用完 `async with` 就 return，session 当时已经失效了。纯 mock 测试完全看不出来——MockProvider 根本不碰 MCP。改用 `AsyncExitStack` 常驻持有，并做了变异验证：回退修复，测试立刻超时失败。

**2. mcp 2.x 直接 401。**
2.x 的 `StreamableHTTPTransport` 不再接受 `headers`，而麦当劳强制要 `Authorization: Bearer <token>`。官方文档和 mcd-mcp-server 仓库都是 1.x 写的。`requirements.txt` 锁死 `mcp>=1.0,<2.0`。

**3. 同一个服务器三种返回形态。**
纯 JSON / markdown 正文 + `## Original Response` + JSON / 散文 + JSON + 尾部散文。而且业务错误信号不是 `isError`，是响应体里的 `success: false`。

**4. 工具参数名全错。**

| 工具 | 真实参数 |
|---|---|
| `query-nearby-stores` | `city` + `keyword` + **必传** `beType` + `searchType` |
| `query-meals` / `query-store-coupons` | `storeCode` + `beCode` + `beType` + `orderType` |
| `order-list` | **不接受任何参数** |
| `calculate-price` | `items[].productCode` |

`beCode` 只有外送/得来速有，到店自提传了会报错。

**5. 历史订单字段名全错。**
实际是 `orderProductList` / `productName`，套餐还多一层 `comboItemList` / `name`。写了个展平函数，**套餐按内层单品计**——画像要回答"我实际吃了什么"，不是"我买了什么套餐"。

**6. 菜单没有价格。**
`query-meals` 只给分类 + code + tags，既没名称也没价格；`query-meal-detail` 有名称仍没价格。价格只在 `calculate-price` 的 `productList` 里（单位：分），而且它同时返回 `productName`——于是 2 次调用能还原完整菜单。坑：单次超过约 30~50 件会报「商品超过数量限制」，得按 30 分批；而且**请求条数会多于返回条数**（部分商品被服务端静默剔除），所以只采信返回结果。

**7. 券后价藏在券标题里。**
真实券是商品型券，标题写着 `11.9元麦辣鸡腿堡`——这个商品原价 ¥22.5。券后价只能从标题的数字里解析。安全约束：解析值 < 原价才替换；直减金额未知时留 0，**绝不编造"省 ¥X"**。

**8. 菜单里混着非正餐条目。**
真实菜单里有 `韩式烟熏芝士风味酱 ¥3.00`、`按摩捶痒痒挠 ¥14.90`。不剔除的话寻优器会一本正经推荐酱料。

另外还有个去重 bug：同价时空券组合先到先得，把命中券的方案挤掉了。改成同价优先用券者。

## 一个反直觉的 bug

评分里"预算利用"项我写的是 `已花/预算`——而任何不超预算的方案这值恒等于 1，**省得越多分完全没体现**。改成"预算内省下多少"之后，最优方案从 ¥24.00 降到 ¥16.90。同一套代码，只是把一个恒等式改成了真正的优化目标。

## 安全

自动花钱的产品，第一优先级不是聪明，是**克制**。五道闸：时间窗口 / 加班证据 / 幂等 / 每日上限 / 22:00 截止。任一不过就降级为人工确认。`dry_run=True` 是默认值。

> 加班证据**未知**和确认**没在**加班是两种状态，但都走同一条路：降级确认。宁可不点，也不误点。
