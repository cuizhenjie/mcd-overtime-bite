## 一、起因

20:47，第八版方案改到第三轮，饿得手抖，打开外卖 App 翻了两屏又退出去——不是不想点，是**不想再做这个决策**。

加班餐的特点是：**低价值、高频率、打断成本极高**。它不需要智力，只需要有人在你不想被打断的时候替你按下"付款"。

所以 OvertimeBite 的入口不是"帮我省多少钱"，而是 **"到点了"**。

```
你还在改第 8 版方案，胃已经在抗议了。
不用起身、不用打开外卖 App、不用纠结点什么——饭会在合适的时候自己安排好。
```

## 二、这个赛道已经有人做省钱了

写之前我先扫了一圈同赛道的作品，发现**主打"省钱/精算"的已经有好几个**。硬刚省钱不划算——那条赛道的优化目标已经被占位了。

所以我把产品重新定位：**入口是时间，省钱降级为预算硬约束**。

| | 省钱类项目 | OvertimeBite |
|---|---|---|
| 起点 | 用户主动提问 | **时间自己走到点** |
| 交付 | 推荐几个方案让人选 | **直接下单** |
| 价格角色 | 优化目标 | **预算硬约束** |
| 关键洞察 | 用券省多少 | **配送费占预算多少** |
| 个性化 | 问用户想吃什么 | **从历史订单自己学** |

省钱的本质是"不浪费"。加班餐的本质是"**别让我在深夜做任何决定**"。

## 三、架构：五步决策链

```
① 该点了吗？   时间窗口 + 加班证据 + 幂等 + 每日上限
② 你在附近哪？ 地址 → 可配送门店（含配送费与 ETA）
③ 你爱吃什么？ 历史订单 → 口味画像
④ 怎么拿？     外送 vs 自取（先渠道，后商品）
⑤ 吃什么？     预算内组合寻优 + 叠券 + 解释排序
```

核心逻辑（触发 / 寻优 / 渠道 / 画像）**零第三方依赖**，全部可以离线跑；MCP 的网络与鉴权细节收敛在单独一层。演示路径和真实路径走的是同一份 pipeline 代码——`MockProvider` 和 `McdDataProvider` 实现同一个协议。

### ① 五道安全闸：自动花钱的产品，第一优先级是克制

| 闸门 | 规则 | 不通过时 |
|---|---|---|
| 时间窗口 | 18:00 ~ 24:00 | 静默跳过 |
| 加班证据 | 必须为真 | **降级为人工确认** |
| 幂等 | 同一 4 小时窗只触发一次 | 跳过 |
| 每日上限 | 默认 1 单 | 跳过 |
| 截止时间 | 22:00 后不自动付钱 | 降级为人工确认 |

注意"加班证据**未知**"和"确认**没在**加班"是两种不同状态，但都走同一条路：降级为人工确认。

> **宁可不点，也不误点。**

以及 `dry_run=True` 是默认值。真实下单是不可逆的外部行为，默认演练、显式关闭，是这类产品应有的默认值。

### ② 口味画像："按我的喜好"得真的来自"我"

偏好只有来自**你本人的历史订单**时才有意义。这里用了贝叶斯收缩：

```python
weight = (count + 3) / (total + 6)      # 向 0.5 收缩
```

两个刻意的设计：

- **无观测证据的品类保持中性 0.5**。"没点过" ≠ "讨厌"。把缺席当厌恶会让画像迅速固化，越用越窄。
- **样本少时向中性收缩**。4 笔全点汉堡，权重也不会冲到 1.0。

冷启动（订单 < 3 笔）时直接返回配置里的先验，不做任何推断。**宁可不学，也不要学错。**

我自己的账户跑出来的画像（9 笔历史订单）：burger 0.44 / side 0.28 / drink 0.28 / chicken 0.19，偏好 spicy，辣度容忍 2/3。

### ③ 先渠道，后商品

这是最容易被忽略、却最值钱的一步。

30 元预算下，5~9 元配送费意味着 **20%~30% 的预算被吃掉**。所以正确的顺序是先把配送费这个常数项定下来：

```
配送费占预算 ≥ 20% 且门店在 800m 内  →  建议到店自取
在工位吃                            →  外送更省事（自取往返是额外成本）
门店不支持外送                       →  到店自取
```

### ④ 寻优：性价比，不是便宜

"价格最优"的真实含义是**花同样的钱，吃得更饱、更合口味**。

```python
score = 0.45 * 饱腹度      # 加班到深夜，抗饿是第一位的
      + 0.30 * 口味匹配    # 来自历史订单的品类/标签权重
      + 0.15 * 预算利用
      + 0.10 * 取餐速度
```

约束是**过滤**而非扣分：忌口、辣度超限直接淘汰；预算超了就是超了。找不到可行解就返回空列表——**绝不为凑数而超预算**。

## 四、真实跑通的结果

接上真实的麦当劳 MCP，用我自己的账户跑了一遍完整链路（门店 → 菜单 → 领券 → 寻优 → 算价）：

```
门店：麦当劳(北京马家堡路餐厅)  1950609   467m
在售餐品：115 个
可用券：3 张（免费脆薯饼 / 人气麦旋风买一送一 / 9.9元中杯冰美式）

最优方案：
  麦辣鸡腿汉堡   原价 ¥22.50  →  券后 ¥11.90
  灰焰圆筒       ¥5.00
  到店取餐
  ─────────────────────────
  合计 ¥16.90      预算上限 ¥30  →  省 ¥13.10
```

这个 ¥16.90 有点反直觉——它不是"最便宜"，是**在预算约束下评分最高的组合**。

> 有个 bug 我一开始没发现：评分里的"预算利用"项用的是 `已花/预算`，而任何不超预算的方案这个值都恒等于 1，**省得越多分反而越高完全没被体现**。改成"预算内省下多少"之后，最优方案从 ¥24.00 降到了 ¥16.90——同一套代码，只是把一个恒等式改成了真正的优化目标。

## 五、踩坑实录：8 个 API 假设，全是错的

这部分是本次开发最有价值的部分，所以单独开一节。**官方文档能查到工具名，但查不到参数形状和返回结构。**

### 1. `ClientSession` 在第一次调用之前就已经死了

MCP 的 `ClientSession` 由 anyio task group 支撑，**一旦它所在的 `async with` 块退出，`__aexit__` 就会 cancel 掉整个 task group**。

我最初的连接协程用完 `async with` 就 return，结果 session 在第一次调用之前就失效了。而这个 bug **在纯 mock 测试里完全看不出来**——`MockProvider` 根本不碰 MCP。

修法是用 `AsyncExitStack` 常驻持有连接，直到 `close()` 才释放。并且做了**变异验证**：把修复回退成提前 `return`，回归测试立刻超时失败。

### 2. `mcp` 2.x 直接 401

2.x 里 `StreamableHTTPTransport` 不再接受 `headers` 参数，而麦当劳 MCP 强制要求 `Authorization: Bearer <token>`，缺头直接 401。

官方文档和 `mcd-mcp-server` 仓库都是按 1.x 写的。`requirements.txt` 因此锁死 `mcp>=1.0,<2.0`，并在注释里写清楚原因。

### 3. 返回形态有三种，同一个服务器

```
① 纯 JSON
② markdown 正文 + ## Original Response + JSON
③ 一段散文 + JSON + 又一段散文
```

而且业务错误的信号**不是** `isError`，是响应体里的 `success: false`。解析器做了三级扫描：优先认带 `success` 的信封，避免被 `data[].storeName` 这种字段骗出空数组。

### 4. 工具参数名全错

| 工具 | 真实参数 |
|---|---|
| `query-nearby-stores` | `city` + `keyword` + **必传** `beType` + `searchType` |
| `query-meals` / `query-store-coupons` | `storeCode` + `beCode` + `beType` + `orderType` |
| `order-list` | **不接受任何参数** |
| `calculate-price` | `items[].productCode` |

`beCode` 只有外送/得来速场景存在，**到店自提传了会直接报错**。

### 5. 历史订单的字段名全错

实际结构是 `orderProductList` / `productName`，套餐还多一层嵌套的 `comboItemList` / `name`。写了个展平函数，**套餐按内层单品计**——因为画像要回答"我实际吃了什么"，而不是"我买了什么套餐"。

### 6. 菜单没有价格

`query-meals` 只给分类 + 商品 `code` + `tags`，**既没有名称也没有价格**；`query-meal-detail` 能拿到名称但仍然没有价格。

真正的价格在 `calculate-price` 的 `productList` 里（单位：**分**），而且它同时返回了 `productName`。于是完整菜单可以用 2 次调用还原出来。

但有两个坑：
- 单次商品数超过约 30~50 会报「商品超过数量限制」，得按 30 分批；
- **请求条数多于返回条数**——部分商品会被服务端静默剔除（不可点/需选配的组合等）。所以只采信返回结果，缺席即视为"当前不可点"。

### 7. 券后价藏在券标题里

真实券是商品型券（`couponId`/`couponCode`/`products[].productCode`），它的标题写着 **`11.9元麦辣鸡腿堡`**——而这个商品原价 ¥22.5。**券后价只能从标题的阿拉伯数字里解析**。

所以有一条安全约束：仅当解析出的券后价 < 原价时才替换。以及，商品型券的直减金额未知时**留 0，绝不编造"省 ¥X"**。

### 8. 菜单里混着非正餐条目

真实菜单里有 `韩式烟熏芝士风味酱 ¥3.00`、`按摩捶痒痒挠 ¥14.90`。不剔除的话，寻优器会一本正经地推荐酱料。

于是加了 `is_non_food()` 过滤，品类判定改用 API 权威的 `categoryName`。

> 还有一个去重 bug：同价时空券组合先到先得，把命中券的方案挤掉了。改成同价时优先用券者。

## 六、工程

- **67 个测试全绿**（`9 + 14 + 15 + 9 + 20`），**全部不需要麦当劳 Token**（集成测试起的是本地自建服务器）
- 集成测试会**真的起一个 MCP 服务器**（streamable-http），走完整 initialize → call，并在服务端侧实测 `Authorization` 头是否送达
- `test_real_responses.py` 的样本**全部来自实际调用结果**，不是手编的
- 核心逻辑**零第三方依赖**；`mcp` SDK 只出现在接入层
