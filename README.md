## 一句话

**基于时间 + 位置 + 你的历史口味 + 30 元预算上限，在加班晚餐时段自动完成领券、选渠道、凑组合、算价、下单。**

## 为什么做这个

加班时的点餐是一次典型的**低价值、高频率、打断成本极高**的决策。

20:00 以后，程序员的身体需要一顿热的，但大脑已经不想做任何决策。打开外卖 App → 翻菜单 → 比价格 → 看配送费 → 凑单 → 付款，这一串动作要占掉约 10 分钟注意力，而那 10 分钟本来该用来休息。

OvertimeBite 把这条链路整个接管。

### 和「省钱点餐」类项目的区别

这个赛道上已经有不少主打省钱的作品。OvertimeBite 的入口是**时间**，省钱只是约束之一：

| | 省钱类项目 | OvertimeBite |
|---|---|---|
| 起点 | 用户主动提问 | **时间自己走到点** |
| 交付 | 推荐几个方案让人选 | **直接下单** |
| 价格角色 | 优化目标 | **预算硬约束** |
| 关键洞察 | 用券省多少 | **配送费占预算多少** |
| 个性化 | 问用户想吃什么 | **从历史订单自己学** |

省钱的本质是"不浪费"。加班餐的本质是"**别让我在深夜做任何决定**"。

## 五步决策链

```
① 该点了吗？   时间窗口 + 加班证据 + 幂等 + 每日上限
② 你在附近哪？ 地址 → 可配送门店（含配送费与 ETA）
③ 你爱吃什么？ 历史订单 → 口味画像
④ 怎么拿？     外送 vs 自取（先渠道，后商品）
⑤ 吃什么？     预算内组合寻优 + 叠券 + 解释排序
```

### ① 触发：三道安全闸

自动花钱的产品，第一优先级不是聪明，是**克制**。

| 闸门 | 规则 | 不通过时 |
|---|---|---|
| 时间窗口 | 18:00 ~ 24:00 | 静默跳过 |
| 加班证据 | 必须为真 | **降级为人工确认** |
| 幂等 | 同一 4 小时窗只触发一次 | 跳过 |
| 每日上限 | 默认 1 单 | 跳过 |
| 截止时间 | 22:00 后不自动付钱 | 降级为人工确认 |

> "加班证据未知"和"确认没在加班"都会降级为需确认——**宁可不点，也不误点**。

### ② 门店

`delivery-query-addresses` → `query-nearby-stores`，一次拿到距离、步行时间、配送费与 ETA。这些数字直接决定第④步的渠道决策。

### ③ 口味画像：从你自己的历史订单里学

"按我的喜好"这句话，只有在偏好来自**你本人的历史订单**时才有意义。

```python
weight = (count + 6 * 0.5) / (total_items + 6)   # 贝叶斯收缩
```

两个刻意的设计：

- **无观测证据的品类保持中性 0.5**。"没点过" ≠ "讨厌"。把缺席当成厌恶会让画像快速固化，越用越窄。
- **样本少时向中性收缩**。4 笔全点汉堡，权重也不会冲到 1.0——样本少就保持保守。

冷启动（订单 < 3 笔）时直接返回配置中的先验，不做任何推断。**宁可不学，也不要学错。**

### ④ 渠道：先渠道，后商品

这是最容易被忽略、却最值钱的一步。

30 元预算下，5~9 元配送费意味着 **20%~30% 的预算被吃掉**。所以正确的顺序是先把配送费这个常数项定下来：

```
配送费占预算 ≥ 20% 且门店在 800m 内  →  建议到店自取
在工位吃                            →  外送更省事（自取往返是额外成本）
门店不支持外送                       →  到店自取
```

### ⑤ 寻优：性价比，不是便宜

"价格最优"的真实含义是**花同样的钱，吃得更饱、更合口味**。

```python
score = 0.45 * 饱腹度      # 加班到深夜，抗饿是第一位的
      + 0.30 * 口味匹配    # 来自历史订单的品类/标签权重
      + 0.15 * 预算利用
      + 0.10 * 取餐速度
```

约束是**过滤**而非扣分：忌口、辣度超限直接淘汰；预算超了就是超了。找不到可行解时返回空列表——**绝不为凑数而超预算**。

### 先领券，再选品

券会改变可行解空间。实例：29 元商品 + 6 元配送 = 35 元超预算，叠加满 30 减 6 + 满 20 减 3 + 汉堡减 4 后 = **28 元**，正好卡进预算。若不先领券，这个方案会被直接判为超预算而放弃。

## 快速开始

### 离线体验（无需 Token）

```bash
python examples/run_demo.py
```

演示覆盖 5 个场景：正常触发、非窗口期不打扰、深夜需确认、无加班证据降级、幂等不重复下单。

### 接入真实麦当劳 MCP

1. 访问 [open.mcd.cn/mcp](https://open.mcd.cn/mcp)，手机号登录后申请 MCP Token
2. 配置连接器：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": { "Authorization": "Bearer YOUR_MCP_TOKEN" }
    }
  }
}
```

3. 安装依赖并配置：

```bash
pip install mcp
export MCD_MCP_TOKEN=<你的token>
```

4. 使用：

```python
import sys; sys.path.insert(0, "src")
from overtime_bite import OvertimeBite, OvertimeConfig
from overtime_bite.mcp_client import McdMcpClient, McdDataProvider

client = McdMcpClient.from_env()
bot = OvertimeBite(McdDataProvider(client), OvertimeConfig(budget_cap_cents=3000))

decision = bot.run(overtime_evidence=True, dry_run=True)   # 默认演练，不会真实下单
print(decision.summary)
```

### 运行测试

```bash
python tests/test_trigger.py     # 9 passed  触发闸门与自动化边界
python tests/test_optimizer.py   # 10 passed 预算硬约束与寻优
python tests/test_pipeline.py    # 15 passed 端到端与下单边界
```

**34 passed**，全程无需 Token、无需网络。

### 为什么把 MCP 接入层单独隔开

核心决策逻辑（触发 / 寻优 / 渠道 / 画像）应当能在**没有 Token、没有网络**的环境下被完整测试。MCP 的网络与鉴权细节全部收敛在 `mcp_client.py`，因此：

- 全部逻辑可离线验证
- 换 MCP 版本时只需改一个文件
- 演示路径与真实路径走的是**同一份 pipeline 代码**（`MockProvider` 与 `McdDataProvider` 实现同一协议）

## 设计取舍

**为什么本地寻优，而不全靠 LLM？**
组合寻优需要枚举与打分，这是确定性计算。交给 LLM 会引入随机性，且无法保证预算硬约束——而"绝不超预算"恰恰是这个产品唯一不可妥协的承诺。

**为什么本地算价后还要 `calculate-price` 复核？**
本地寻优器只负责**生成候选**，不负责裁决价格。最终金额一律以麦当劳侧返回为准，并覆盖本地估算，保证展示金额与实际扣款永远一致。

**为什么默认 `dry_run=True`？**
自动下单是不可逆的外部行为。默认演练、显式关闭，是这类产品应有的默认值。
